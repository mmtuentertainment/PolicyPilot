<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Clerk dashboard → `.env.local` | Clerk secret key crosses from dashboard clipboard into a local file. Trust boundary because the secret key authenticates server-side as the Clerk app — leakage = full impersonation. |
| Supabase dashboard → `.env.local` | Service-role key has bypass-RLS privilege. Leakage = bypassing the entire multi-tenancy gate. |
| `.env.local` → git | Must NOT cross. `.gitignore` is the only gate. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Information disclosure | `.env.local` committed to git | mitigate (HIGH severity) | Task 3 verifies `git check-ignore -v .env.local` exits 0 BEFORE the task is marked done. The `.gitignore` already has `.env.local` on line 2 from existing repo state. |
| T-02-02 | Information disclosure | Clerk / Supabase secrets printed to terminal logs during sanity check | mitigate | Task 3's sanity check uses `process.exit(0/1)` only — it never `console.log`s the secret values. Sentinel substrings (`pk_test_`, `sk_test_`, `postgresql://`) are printed only on failure to identify *which* key is missing, never on success. |
| T-02-03 | Spoofing | Operator pastes the wrong key (e.g. publishable swapped with secret) | mitigate | Task 3 asserts the `pk_test_` and `sk_test_` prefixes — Clerk publishable keys start with `pk_test_` (or `pk_live_`), secret keys with `sk_test_` (or `sk_live_`). A swap would fail the sentinel check. |
| T-02-04 | Spoofing | Operator pastes direct (5432) URI instead of pooler (6543) URI | mitigate | Task 3 asserts the substring `pooler.supabase.com:6543`. D-06 mandates the pooler for runtime. |
| T-02-05 | Tampering | Operator forgets to enable Clerk Organizations | accept-then-detect | Phase 2 webhook handler will fail-loudly if Organizations isn't enabled (no `organization.created` events arrive). Surfacing now in Task 1 is the strongest practical mitigation; verifying enablement programmatically requires the very secret key the operator is in the process of pasting. |
| T-02-06 | Elevation of privilege | `SUPABASE_SERVICE_ROLE_KEY` imported by a Client Component | mitigate (cross-phase) | Plan 04 (Drizzle skeleton) gates this — `lib/db/index.ts` is server-only and uses `DATABASE_URL`, not the service-role key. Phase 2 reinforces with an explicit "server-only" lint rule. Phase 1 does not consume the service-role key — it's collected for Phase 2 onward. |

**ASVS L1 severity assessment:** T-02-01 is HIGH severity (secret leak via VCS). Fully mitigated by the explicit gitignore-check gate in Task 3 acceptance criteria — the task cannot pass without that check exiting 0.
</threat_model>
